# V1 현황 진단

## 1. 요약

V1은 이터널 리턴 커뮤니티 내전을 위한 운영 도구다. 선수 등록과 티어 관리, 출석, 팀 드래프트, 점수 입력, 경기 종료 기록, 전적 조회를 하나의 정적 웹 앱에서 제공한다.

핵심 기능은 이미 한 흐름으로 연결되어 있지만, 데이터 구조가 현재 경기 상태를 `players` 행에 직접 덮어쓰는 방식이고 UI·도메인·DB 로직이 페이지별 JavaScript에 섞여 있다. 따라서 기능 추가보다 데이터 정합성, 권한, 테스트 가능성이 먼저 한계에 도달할 구조다.

## 2. 현재 기술 구성

| 영역 | 현재 상태 |
|---|---|
| UI | HTML 9개, CSS 10개, 페이지별 Vanilla JavaScript (2026-10-23 문의 페이지 제거 후) |
| 데이터/API | 브라우저에서 Supabase JS SDK 직접 호출 |
| 인증 | Supabase Auth 세션 확인 후 클라이언트에서 페이지 이동/메뉴 숨김 |
| 배포 | 정적 호스팅을 전제로 보이며 Electron `main.js`도 존재 |
| 빌드 | 저장소에 `package.json`과 잠금 파일 없음 |
| 테스트 | 자동 테스트와 CI 설정 없음 |
| DB 변경 관리 | migration/seed/schema 파일 없음 |
| 관측성 | `console.log`, `alert` 중심 |

2026-10-23 운영자 선택에 따라 V1의 Live Server(`localhost`/`127.0.0.1`)와 배포 사이트는 같은 운영 Supabase 프로젝트를 사용한다. 로컬 화면의 저장·삭제도 운영 데이터에 즉시 반영된다. V1은 V2 개발 프로젝트에 연결하지 않는다.

README는 Electron 실행과 빌드를 설명하지만 실제 `package.json`이 없어 현재 체크아웃만으로는 해당 절차를 재현할 수 없다.

## 3. 사용자 흐름과 데이터 흐름

### 운영 흐름

1. 관리자가 선수 정보를 등록하고 티어·코스트를 조정한다.
2. 출석 페이지에서 `players.status`를 `present` 또는 그 외 상태로 변경한다.
3. 드래프트가 출석 선수만 읽어 `players.team_id`를 갱신한다.
4. 점수판이 팀별 선수를 읽고 `match_scores`에 라운드 점수를 저장한다.
5. 경기 종료 시 집계 결과를 `hall_of_fame.match_detail` JSON으로 복사한다.
6. 공개 화면은 현재 선수/점수와 누적 기록을 다시 계산해 보여준다.

### 현재 테이블 사용 현황

| 테이블 | 실제 코드에서의 역할 | 주요 필드 |
|---|---|---|
| `players` | 선수 마스터 + 출석 + 현재 팀 배정 | `id`, `name`, `tier`, `cost`, `status`, `team_id`, `image_url` |
| `match_scores` | 현재 경기의 팀·라운드별 점수 | `id`, `team_id`, `round_num`, `score` |
| `hall_of_fame` | 종료 경기 스냅샷과 우승 기록 | `created_at`, `team_name`, `members`, `total_score`, `match_detail` |
| `inquiries` | 기존 문의 데이터 보존 (2026-10-23 페이지 제거) | `sender`, `category`, `content`, `status` 등 |
| `scores` | 구형 대시보드 코드에서만 조회 | README에도 이 이름으로 기재 |

현재 경기라는 독립 엔터티가 없어 모든 사용자가 하나의 전역 경기 상태를 공유한다. 과거 경기 정보는 정규화된 참가/팀/점수 행이 아니라 `hall_of_fame`의 문자열과 JSON에 의존한다.

## 4. 잘된 점

- 운영 순서에 맞춰 기능이 나뉘어 있어 도메인 경계 후보가 명확하다.
- Supabase Auth와 공개/관리자 화면의 구분이 이미 존재한다.
- 드래프트는 자동 배정 뒤 수동 스왑과 확정 저장을 지원한다.
- 경기 종료 결과를 스냅샷으로 보존해 과거 화면이 현재 선수 정보 변경에 덜 흔들린다.
- 테마와 페이지별 스타일이 분리되어 있어 디자인 토큰으로 발전시킬 기반이 있다.

## 5. 확인된 문제와 위험

### P0 — 즉시 대응

#### Discord 웹훅 비밀값 노출

2026-10-23 V1 보안 수정에서 문의 페이지와 전용 JavaScript/CSS, 메뉴 링크를 제거했다. `inquiries`의 기존 운영 데이터는 삭제하지 않았다. 이미 배포된 코드와 Git 이력에 노출된 기존 웹훅은 비밀로 취급할 수 없으므로 운영자가 즉시 폐기해야 한다.

조치:

1. 기존 웹훅을 즉시 폐기한다.
2. 문의 기능을 다시 도입할 때 새 값은 저장소와 브라우저 번들에 넣지 않고, 서버 측에서 검증·횟수 제한 후 전송한다.

#### 운영 DB의 RLS 비활성화 확인

2026-10-23 운영 프로젝트 `cduroqwecrhfkhtgxwru`를 읽기 전용으로 확인한 결과, `public.players`, `scores`, `hall_of_fame`, `inquiries`, `match_scores` 모두 RLS가 꺼져 있고 정책이 없다. 관리자 페이지의 클라이언트 리다이렉트와 메뉴 숨김은 DB 쓰기 권한을 보호하지 않는다. 실제 권한과 호환되는 정책을 준비한 뒤 RLS를 적용해야 한다. 정책 없이 RLS만 켜면 현재 사이트의 데이터 조회와 저장이 중단될 수 있다. 운영 영향과 정책 초안은 [`../V1_RLS_REVIEW.md`](../V1_RLS_REVIEW.md)에 기록했다.

조치:

- 모든 테이블의 RLS 활성화 여부와 정책을 내보내 migration으로 관리한다.
- 공개 읽기와 관리자 쓰기를 정책으로 분리한다.
- 관리자 여부는 단순 로그인 여부가 아니라 서버가 신뢰할 수 있는 role/claim/profile로 판정한다.

### P1 — V2 기반 작업 전에 해결

#### 데이터 계약 불일치

- README와 `assets/js/index.js`는 `scores`와 `round`를 전제로 한다.
- 실제 점수판과 새 대시보드는 `match_scores`와 `round_num`을 사용한다.
- `assets/js/index.js`와 `assets/js/home.js`가 모두 대시보드 구현처럼 남아 있다.
- README에는 실제로 사용하는 `inquiries`와 `match_scores` 정의가 없다.

하나의 canonical schema를 정하고 기존 이름을 호환 뷰로 잠시 유지하거나 migration으로 일괄 전환해야 한다.

#### 대시보드 동률 정렬 결함

`home.js`는 동점일 때 `a.id - b.id`로 정렬하지만 `calculateTeamStandings()` 반환 객체에는 `id`가 없다. 결과적으로 동점 팀의 정렬이 안정적으로 보장되지 않는다.

#### 팀 저장의 비원자성

드래프트 저장은 모든 선수의 `team_id`를 먼저 `null`로 만든 후 선수별 업데이트를 병렬 실행한다. 중간 실패 시 전체 팀 배치가 일부만 저장될 수 있고, 각 요청의 오류도 충분히 확인하지 않는다.

V2에서는 DB 함수/RPC 또는 트랜잭션으로 한 번에 확정해야 한다.

#### 전역 현재 상태

`players.status`, `players.team_id`, 전역 `match_scores`가 현재 이벤트를 표현한다. 동시에 둘 이상의 경기나 테스트 경기를 운영할 수 없고, 초기화·종료 시점의 실수로 데이터가 섞일 수 있다.

### P2 — 기능 이관 중 개선

- 문자열로 저장된 참가자 이름은 닉네임 변경, 쉼표 포함, 동명이인에 취약하다.
- 2026-10-23 V1 보안 수정에서 현재 화면의 DB 문자열 출력에 HTML 이스케이프 및 이미지 URL 검증을 적용했다. 신규 출력 경로를 추가할 때도 같은 경계를 유지해야 한다.
- Supabase SDK와 Font Awesome을 CDN에 의존해 Electron/오프라인 실행 재현성이 낮다.
- `attendance.html`은 Supabase SDK를 두 번 불러온다.
- 테마 로직이 `theme.js`와 `theme-manager.js`로 중복되어 있다.
- 사이드바 마크업과 내비게이션이 각 HTML에 복제되어 변경 누락 가능성이 크다.
- 오류 처리가 `alert`와 콘솔에 집중되어 운영자가 부분 실패를 판단하기 어렵다.
- 자동 드래프트의 랜덤 결과에 seed/기록이 없어 동일 조건 재현이 불가능하다.
- 페이지 모듈이 DOM, 도메인 계산, DB 호출을 함께 담당해 단위 테스트가 어렵다.

## 6. 저장소 밖에서 확인해야 할 사항

다음은 코드만으로 확정할 수 없다.

- 운영/개발 Supabase의 상세 제약조건, 인덱스, 트리거
- 운영 DB의 관리자 권한 모델에 맞는 RLS 적용 방식
- 관리자 계정과 role 부여 방식
- 현재 배포 대상과 URL, Electron을 실제로 사용하는지 여부
- 운영 데이터 양, 보존 정책, 백업/복구 절차
- 이터널 리턴 점수 규칙과 체크포인트 규칙의 확정 사양
- V2에서 동시에 여러 대회/경기를 운영해야 하는지 여부

이 항목을 확인하기 전에는 V1 DB에 파괴적 migration을 적용하지 않는다.

## 7. V2 착수 판단

V1을 그대로 확장하는 것보다 경기 중심 데이터 모델을 먼저 도입하는 편이 안전하다. 다만 전체 재작성은 운영 공백과 데이터 이관 위험이 크므로, V1을 읽기 가능한 상태로 유지하면서 V2 스키마와 화면을 기능 단위로 교체하는 방식을 권장한다.
